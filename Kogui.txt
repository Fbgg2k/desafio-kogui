Objetivo
A aplicação será desenvolvida com integração a PokéAPI, permitindo a exibição da listagem de Pokémons em formato de cards interativos. O sistema oferecerá funcionalidades para que o usuário marque seus Pokémon favoritos e selecione até seis para compor uma equipe de batalha personalizada.

Regras
O usuário poderá adicionar qualquer Pokémon à lista de favoritos. No entanto, apenas seis poderão ser selecionados para compor o Grupo de Batalha. Ambos os estados (favorito e integrante do grupo) deverão ser destacados na listagem com os itens específicos de menu dedicadas.

Modelagem dos Objetos Relacionais

Requisitos Mínimos (OBRIGATÓRIOS)

5. Utilizar Base de Dados Local SQLite com uso de SQLAlchemy ou ORM Django

Resumo das entidades
- Usuario: representa os usuários do sistema.
- Pokémon: representa os Pokémons disponíveis.
- PokémonUsuario: relação entre um usuário e um Pokémon específico, com informações adicionais da relação.
- TipoPokémon: tipos de Pokémon (Fogo, Água, etc.).

Relações entre as tabelas
1) Usuario 1:N PokémonUsuario
- Um usuário pode ter vários registros em PokémonUsuario (um para cada Pokémon associado ao usuário, seja como favorito ou como Pokémon na equipe).
- Cardinalidade: Um Usuario possui N PokémonUsuario.
- Chave estrangeira: PokémonUsuario.IdUsuario referencia Usuario.IDUsuario.

2) Pokémon 1:N PokémonUsuario
- Um Pokémon pode aparecer em muitos registros de PokémonUsuario, pois diferentes usuários podem ter o mesmo Pokémon listado (ou diferentes instâncias/favores do mesmo Pokémon).
- Cardinalidade: Um Pokémon possui N PokémonUsuario.
- Chave estrangeira: PokémonUsuario.IDPokémon referencia Pokémon.IDPokémon.

3) Pokémon 1:N TipoPokémon (quando representado como relacionamento direto)
- Se cada Pokémon possuir apenas um Tipo1 (e possivelmente Tipo2), a relação é:
  - Pokémon.Tipo1 referencia TipoPokémon.IDTipoPokémon
  - Opcionalmente, Pokémon.Tipo2 referencia TipoPokémon.IDTipoPokémon (quando houver um segundo tipo)
- Cardinalidade: Um Pokémon possui 1 ou 2 tipos, cada tipo é uma referência a um registro de TipoPokémon.
- Observação: TipoPokémon é uma tabela de referência (dicionário) com descrições de tipos e fraquezas.

Diagrama conceitual de relacionamento (texto)
- Usuario (IDUsuario PK)
  - outros atributos (Nome, Email, etc.)
  - 1:N
    - PokémonUsuario (IDPokémonUsuario PK, IDUsuario FK, IDPokémon FK, …)
- Pokémon (IDPokémon PK)
  - Nome, Descrição, Tipo1 (FK -> TipoPokémon), Tipo2 (FK -> TipoPokémon, opcional), etc.
  - 1:N
    - PokémonUsuario (IDPokémonUsuario PK, IDUsuario FK, IDPokémon FK, …)
- TipoPokémon (IDTipoPokémon PK)
  - Descrição, Fraquezas
  - 1:N para Pokémon (a partir de Tipo1 e Tipo2)

Camadas práticas (exemplos de chaves e colunas)
- Usuario
  - IDUsuario (PK)
  - Nome
  - Login
  - Email
  - Senha
  - DataNascimento
  - etc.

- Pokémon
  - IDPokémon (PK)
  - Nome
  - Descrição
  - Tipo1ID (FK -> TipoPokémon.IDTipoPokémon)
  - Tipo2ID (FK -> TipoPokémon.IDTipoPokémon, NULLABLE)
  - Geração
  - Número

- TipoPokémon
  - IDTipoPokémon (PK)
  - Descrição
  - Fraquezas

- PokémonUsuario
  - IDPokémonUsuario (PK)
  - IDUsuario (FK -> Usuario.IDUsuario)
  - IDPokémon (FK -> Pokémon.IDPokémon)
  - Nome (opcionalmente duplicado do Pokémon para registro da relação)
  - Descrição (opcional, para anotações da relação)
  - TipoPokémon (se necessário registrar o tipo específico na relação, ou isso pode ser inferido pela  Pokémon.Tipo1ID/Tipo2ID)
  - Itens (lista ou referência a itens do Pokémon na interface)
  - DataFavorito (ou booleans para indicar se é favorito)
  - EmGrupoDeBatalha (boolean ou posição no grupo)

Notas de implementação
- A relação entre Usuario e PokémonUsuario modela o relacionamento muitos-para-muitos indiretamente, com a tabela PokémonUsuario atuando como a associação com atributos adicionais (favorito, data de adição, etc.).
- Se quiser manter a semântica de “Team” (Grupo de Batalha), você pode:
  - Adicionar na PokémonUsuario um atributo isFavorito boolean, isNoGrupo boolean, e uma posiçãoNoGrupo ou IDGrupo para suportar equipes.
  - Alternativamente, criar uma entidade GrupoDeBatalha com relação 1:N para PokémonUsuario contendo: IDGrupo, IDUsuario, NomeGrupo, etc., e associar PokémonUsuario a um grupo específico.
- Para normalizar, armazene Tipo1ID e Tipo2ID em Pokémon como chaves estrangeiras para TipoPokémon. Evita duplicação de dados de tipo entre pokémons.

### **FASE 5: Docker e Deploy (Dia 12)**

#### Passo 5.1: Criar Dockerfiles

**backend/Dockerfile:**
```dockerfile
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 5000
CMD ["python", "run.py"]
```

**frontend/Dockerfile:**
```dockerfile
FROM node:18 as build
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
RUN npm run build

FROM nginx:alpine
COPY --from=build /app/dist/kogui-frontend /usr/share/nginx/html
EXPOSE 80
```

#### Passo 5.2: Criar docker-compose.yml
```yaml
version: '3.8'
services:
  backend:
    build: ./backend
    ports:
      - "5000:5000"
    environment:
      - FLASK_ENV=development
    volumes:
      - ./backend:/app
  
  frontend:
    build: ./frontend
    ports:
      - "4200:80"
    depends_on:
      - backend
```

#### Passo 5.3: Testar com Docker
```bash
docker-compose up --build
```
